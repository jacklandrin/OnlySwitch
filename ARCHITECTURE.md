# OnlySwitch Architecture

## Purpose

OnlySwitch is a macOS menu-bar utility that exposes system switches, widgets, an optional desktop pet, an AI assistant, and remote control capabilities. The repository also contains reusable Swift Package modules, a widget target, a remote app, persistence, networking, authentication, and OpenClaw integration.

## Core constraints

1. **Use The Composable Architecture (TCA).** Model user-facing features with state, actions, reducers, and effects using [pointfreeco/swift-composable-architecture](https://github.com/pointfreeco/swift-composable-architecture). OnlySwitch already uses TCA in multiple package features; extend that pattern consistently.
2. **Use `swift-dependencies` for injection.** Runtime services and external effects should be accessed through `@Dependency` using [pointfreeco/swift-dependencies](https://github.com/pointfreeco/swift-dependencies), rather than being constructed directly inside views or reducers. When introducing or migrating a service, add the dependency at the appropriate module boundary.
3. **Modularize with Swift packages.** Use the `Modules` Swift Package to separate independently buildable and testable functionality. Keep target dependencies intentional and acyclic.
4. **Factor monolithic logic into focused modules.** Extract switch behavior, feature state, persistence, networking, remote protocol, authentication, AI provider integrations, and presentation concerns into focused modules as boundaries become clear.
5. **Keep SwiftUI views free of business logic.** Views render state and send user intent. Business rules, validation, orchestration, permissions, shell/AppleScript effects, and state transitions belong in reducers, domain types, or injected clients.
6. **Follow Swift 6 concurrency safety.** Preserve `Sendable` correctness, actor isolation, structured concurrency, cancellation, and safe crossing of process, networking, persistence, and app/extension boundaries.
7. **Extract common logic for reuse.** Shared models, remote protocol types, switch descriptors, formatting, validation, persistence adapters, and permission policies should have one well-defined implementation and be reused by the app, widget, remote app, and package targets where appropriate.

## Intended dependency direction

```text
App / Widget / Remote app targets
        ↓
Feature modules (TCA reducers, feature state, feature views)
        ↓
Domain modules (switches, remote protocol, models, business rules)
        ↓
Infrastructure modules (system effects, persistence, networking, AI providers, keychain)
```

Infrastructure details must not leak into SwiftUI views. Feature modules should depend on domain abstractions and access infrastructure through injected dependency clients. Shared protocol and model modules must remain safe for all targets that exchange their values.

## Thin app targets

Following pointfreeco/isowords, every line of code lives in the `Modules` Swift package. Xcode targets contain only an entry point, resources, Info.plist, and entitlements:

| Target | Entry file | Root module |
| --- | --- | --- |
| OnlySwitch (macOS) | `OnlySwitch/main.swift` → `AppEntry.run()` | `AppFeature` |
| OnlySwitchRemote (iOS) | `OnlySwitchRemote/App/OnlySwitchRemoteApp.swift` → `OnlyRemoteRootView` | `OnlyRemoteFeature` |
| OnlyWidgetExtension | `OnlyWidget/OnlyWidgetBundle.swift` | `OnlyWidgetFeature` |
| OnlySwitchPrivilegedHelper | `OnlySwitchPrivilegedHelper/main.swift` | `PrivilegedHelperCore` |

Shared low-level modules: `OnlySwitchObjC` (private-framework headers and Objective-C, linked against `DisplayServices`/`CoreBrightness`), `OnlySwitchPersistence` (Core Data model in its own resource bundle, hand-written `NSManagedObject` subclasses with stable `@objc` names, shared by app and widget), and `PrivilegedHelperCore` (XPC contract shared by app and helper).

The widget's App Intents (configuration intents and entities) live in `OnlyWidgetFeature`, which exposes them through `OnlyWidgetFeaturePackage: AppIntentsPackage`; the extension's `OnlyWidgetExtensionPackage` includes it so the metadata processor extracts them into the extension.

Asset catalogs and string catalogs remain in the targets and are read via `Bundle.main`. Xcode does not extract strings from package code into the target catalogs: add keys manually and never run "Remove stale strings". `AppFeature` and `OnlyRemoteFeature` are deliberately coarse; split them into focused feature modules incrementally. `Scripts/check-thin-targets.sh` enforces this layout.

Test targets live in `Modules/Tests` and run from the app schemes' Test actions. The `Modules-Package` scheme cannot be tested as a whole on macOS because `OnlyRemoteFeature` is iOS-only, so `OnlySwitch.xcscheme` is the single macOS test entry point and lists every macOS package test target; add new macOS test targets there. Remote tests (`OnlyRemoteFeatureTests`) run from the `OnlySwitchRemote` scheme on an iOS simulator. Known limitation: plain `swift build`/`swift test` in `Modules/` cannot resolve the package graph because `swift-issue-reporting` and `xctest-dynamic-overlay` both declare an `IssueReporting` target; build and test through the Xcode schemes.

## Current repository boundaries

- `Modules/` is the primary Swift Package boundary. It contains feature modules such as `OnlyControl`, `OnlyAgent`, `Authenticator`, `StickerView`, and `DesktopPet`, plus shared `Defines`, `Extensions`, `Utilities`, `Networking`, `RemoteCore`, and `RemoteTransport` modules.
- `Modules/Sources/OnlyAgent/Conversation` owns Only Agent: a TCA `AgentConversationReducer` that turns a prompt into either clarifying questions or a plan of AppleScript/Shell steps. Each turn collects a fresh `AgentSystemInfo` snapshot (macOS version and build, chip architecture, Mac model identifier, memory, preferred language, region, display count, appearance, Finder hidden-files and Dock auto-hide state, Homebrew path; never user, computer or serial identifiers; the empty conversation's starter suggestions are derived from the same snapshot so they always describe a change) and sends it in `AgentPromptBuilder` system instructions with a bounded transcript through `ModelProviderService.instructedChatStream` (`.agent` purpose; Codex keeps one thread per conversation), and `AgentReplyParser` tolerantly decodes the single-JSON-object reply contract. Scripts run only through the injected `AgentConversationClient.run` (`AgentScriptRunner`: shell steps as a `/bin/sh -c` process with no stdin, reporting stderr and exit status, terminated with all descendants on Stop, and given a per-run `SUDO_ASKPASS` helper that asks for the administrator password inline through private FIFOs in a 0700 temporary directory, so `sudo -A` and Homebrew work while the password is never stored in reducer state, logged or sent to the model; AppleScript steps in-process via OSAKit with the real OSA error message; the shared `runAppleScript(isShellCMD:)` helper is not used because it does not escape quotes); "Preview first" (default, persisted) never runs without a tap, "Run directly" runs a fresh plan immediately, and a failed or stopped step skips the rest. A fully succeeded plan can be saved through `AgentEvolutionClient`, whose live value is supplied by `AppFeature`, as one user-authored AppleScript Evolution button composed by `EvolutionScriptComposer` (never privileged); shell steps that use sudo or Homebrew get `SUDO_ASKPASS` pointing at a persistent helper in Application Support that shows a native password dialog. The stored model selection (`SharedKey.currentAIModel`, its file path and JSON shape) is a compatibility contract: it is read on appear and written only by explicit selection. `AICommanderSwitch` hosts the window, which Evolution settings can also open; the Evolution editor reuses the same model selection for inline script generation (see Evolution settings).
- `Modules/Sources/Aphrodite` owns the generated mini-app authoring domain, serialized library, TCA feature, and sandboxed renderer. `SettingsVM.shared` retains the Settings store for the app session so accepted work survives presentation changes, while Aphrodite's injected notification boundary requests permission and reports only persistence-confirmed completion; the app delegate owns foreground banner policy. Authoring prompts, conversation history, model selection, and other authoring configuration never cross the `RemoteCore` or `RemoteTransport` boundary; validated runtime HTML, optional validated SVG, and minimal display metadata may cross that boundary for OnlyRemote. Each app persists only its latest HTML and compact completed user prompts; optimistic replacement prevents a stale edit from restoring a deleted or newer app. Six bundled starter apps are merged into the local library once using stable IDs and a persisted seed version, preserving user edits and deletions. Codex reuses a runtime per model and purpose while mapping each Aphrodite conversation to its own thread. Optional icons come from the same model response as static SVG, are validated before storage and native rendering, and fall back to `star.hexagon` when unavailable. Existing libraries without icons or conversation metadata remain readable. The renderer's only native signals are bounded content-size reports from an isolated WebKit content world; the editor keeps an unscaled logical canvas and scales it to fit its preview, while launchers use the content-height signal. Generated page JavaScript cannot access the handler or any native capability.
- `Modules/Sources/AppFeature` (entered from the thin `OnlySwitch` target) contains the main macOS application, system integrations, Core Data persistence, audio/player functionality, and app-specific UI. Menu-bar hosts measure active content separately from persistent chrome, then apply the shared `Utilities.AdaptivePanelHeightPolicy` to the hosting screen’s `visibleFrame`. Only Control uses a fixed-size window and keeps overflow scrollable.
- `Modules/Sources/OnlyWidgetFeature` (entered from the thin `OnlyWidget` target) contains widget-facing code and must use extension-safe shared models and effects.
- `Modules/Sources/OnlyRemoteFeature` (entered from the thin `OnlySwitchRemote` target) contains the remote-control application and must share protocol contracts without importing main-app implementation details. Its root TCA feature owns the independent Aphrodite, Sound Mixer, Brightness and Screenshots tabs and the OnlyRemote Plus sheet. Access to those four tabs is gated by verified subscription entitlement through the shared `RemotePlusAccessFeature`, with an embedded `RemotePlusGateView` paywall for nonmembers (see OnlyRemote tabs). Entitlement refresh is independent of product loading and responds to foregrounding, transaction updates, purchases, restoration, and expiration. A Debug-only Settings submenu provides a persisted paywall bypass for development; Release builds ignore this preference. The injected StoreKit client loads and purchases only the one-month `jacklandrin.onlyremote.plus.monthly` auto-renewable product. Only eligible verified transactions unlock access; pending purchases await a later transaction update, and cancellation does not grant access. Recognized verified transactions are finished after processing, and purchase results update both embedded and Settings paywalls without depending on duplicate transaction notifications.
- `RemoteCore` owns the lightweight, versioned Aphrodite transfer models and the shared HTML and SVG safety validators. Authenticated protocol 1.6 sessions automatically transfer the complete saved library as bounded manifests and 64 KiB chunks with SHA-256 integrity; the wire contract excludes Aphrodite authoring types and private authoring state. OnlyRemote validates each complete transfer before atomically replacing its per-Mac cache, and its WebKit runner uses the same isolated custom origin, content-security policy, and navigation restrictions as the shared sandbox primitives. OnlyRemote lists and runs cached tools but does not create or edit them.
- Launch Campaign uses an injected TCA client to fetch a bounded manifest and dated HTML from the fixed repository origin. A nonpersistent, navigation-restricted WebKit renderer loads while hidden and acknowledges the date only after successful presentation. The page follows app language and native appearance; its OnlyRemote download link opens the existing native QR window. Both windows temporarily rise above menu-bar panels when presented and return to normal level on focus loss, app deactivation, or closing. Failed requests or rendering remain silent and unacknowledged. Debug builds bypass the previously shown date so the latest page appears on every app launch; forced previews do not modify the saved presentation date.
- `Modules/Tests/AppFeatureTests`, `Modules/Tests/OnlyRemoteFeatureTests`, and the other `Modules/Tests/` targets contain unit, integration, feature, protocol, and end-to-end coverage.
- `OpenClaw/skills/onlyswitch-deeplink/` contains the OpenClaw integration documentation and skill for invoking built-in switches through deeplinks.

The project already uses TCA in package features and Swift Package modularization. New work should extend existing reducer/dependency patterns rather than introduce a parallel state-management approach. `swift-dependencies` is an architectural requirement for new injectable services; existing direct constructions may be migrated incrementally at feature boundaries.

## Feature structure guidance

Each feature should aim to contain:

- a `State` value representing renderable state;
- an `Action` enum representing user, lifecycle, and dependency-driven events;
- a reducer that owns transitions and effects;
- a SwiftUI view that observes state and sends actions;
- injected clients for clocks, system commands, permissions, persistence, networking, and AI providers;
- focused tests for business rules, effect behavior, authorization failures, and important edge cases.

## System and remote boundaries

Changes to switches, shell commands, AppleScript, keychain data, Core Data, widgets, remote sessions, or deeplinks must account for:

- macOS authorization and user-cancelled permission flows;
- command failure, unavailable hardware, unsupported OS versions, and missing executables;
- secure storage and migration of credentials, pairing data, and provider keys;
- remote pairing, authentication, encryption, framing, ordering, replay protection, cancellation, and reconnect behavior;
- widget refresh limits and stale state;
- process isolation and extension-safe serialization;
- localization, accessibility, and menu-bar interaction behavior.

## Testing expectations

Prefer deterministic reducer and domain tests with controlled dependencies. Add integration coverage for Core Data, system-effect adapters, remote transport, pairing, and cross-target behavior when reducer tests cannot prove correctness. New concurrency-sensitive code should include tests for cancellation, ordering, actor isolation assumptions, malformed frames, connection loss, and failure propagation where applicable.

## Crash report notice

The macOS app records an initial cutoff before entering SwiftUI. After a successful launch, `CrashReportPrompt` uses an injected client to look for the newest matching system `.ips` report newer than that cutoff. Discovery runs off the main thread and inspects bounded metadata from regular files in the current user's DiagnosticReports folder. OnlySwitch's macOS bundle identity and the system crash report type must match. The localized AppKit alert advances the cutoff after dismissal, whether or not the user chooses to reveal the report in Finder. No match leaves the cutoff unchanged so a report written after the scan remains eligible at a later launch. The launch campaign waits for discovery and is deferred to another launch if the alert is shown. Test hosts and the hosted audio helper do not run crash report discovery. OnlySwitch does not install a crash handler, change system settings, or upload reports.


## Tab visibility

Settings → Tabs is the single place to show or hide the optional list/OnlyControl tabs (`SectionBar.Section.manageable`; Controls is always shown). `TabVisibilityClient` maps each tab to its source of truth: Authenticator and Sound Mixer keep their feature `enabled` flags, every other tab its exportable `show…TabKey` default (missing means visible). `TabVisibilitySettingsVM` writes through the client and posts `.changeSettings`, which the list and OnlyControl hosts already observe. Per-feature settings pages no longer carry their own "show tab" toggles.

The built-in switches that only toggled a tab (`SwitchType.deprecatedTabVisibilitySwitches`: Authenticator, Sound Mixer, System Monitor, Codex Usage, Claude Usage, Aphrodite, Xcode Cleaner, App Uninstaller) are deprecated. Their enum cases and legacy identifiers remain so stored bitmasks and old remote IDs decode, but `SwitchType.offeredCases` excludes them from the switch list, Customize, keyboard shortcuts, widget entities, the OnlyRemote catalog and live remote command routing.

## Schedules

`Modules/Sources/Scheduler` owns the schedule domain (`Schedule`, target, action, trigger, run outcome), the pure `ScheduleCalendar` next-fire calculation, draft validation, the localized `ScheduleFormatter`, the TCA `SchedulesFeature` (list, CRUD and timing engine) and `ScheduleEditorFeature`, and their views (Settings master/detail editor and the list/OnlyControl tab). The module ships only the `UserDefaults` storage client; the app supplies the executor, notification and system-event clients (`ScheduleClients+App.swift`). The executor reuses `RemoteCatalogProvider` for the target picker and `RemoteCommandRouter` for execution, so schedules can run exactly what OnlyRemote can, through the same validation, and have no other execution path. Switches and players take Turn On/Off (`.setState`); buttons, Shortcuts and button-type Evolutions take Run (`.trigger`); there is no toggle action. A schedule keeps the target title captured at save time, so a deleted Shortcut or Evolution stays listed as unavailable and records a failed outcome when it fires.

A schedule's anchor is the later of `activatedAt` and `lastFiredAt`; activating it or saving a changed trigger resets `activatedAt` to now, so saving never fires immediately. Each tick runs every schedule whose first fire after the anchor is due, in pending-date order, then sets `lastFiredAt` to now, so fires missed while asleep, quit or after a clock jump catch up once and then resume the normal cadence. A schedule that is still running when it comes due again is skipped (the anchor advances; nothing queues); Run Now also works for inactive schedules and does not move the anchor. Privileged switches may show their usual password or permission prompt when they fire unattended; a cancelled prompt records a failed outcome. The engine sleeps on the injected clock until the next fire but never longer than 60 s, and also ticks on wake, system clock and time-zone change notifications; the injected wall clock is the source of truth. Weekly and hourly triggers use `Calendar.nextDate(…, matchingPolicy: .nextTime)` in the current calendar and time zone: a time skipped by DST fires at the next valid instant, a weekly time in a repeated hour fires once, and hourly triggers fire in both copies of a repeated hour. Intervals are limited to 10 s…7 days; an empty weekday set means every day.

The list is saved synchronously from the reducer, in mutation order, as a JSON array under `schedulesKey`. Undecodable data loads as an empty list, shows a notice and is not overwritten until the user saves a schedule. The list is not part of settings export/import; `showSchedulesTab` is exportable and, like other optional tabs, is edited through `TabVisibilityClient` on Settings → Tabs. `SettingsVM.shared.schedulesStore` is the single session store shared by Settings, the menu-bar list and OnlyControl; AppDelegate starts it at launch so schedules fire with no window open, and they run only while OnlySwitch is running. Notifications are opt-in per schedule: authorization is requested the first time the toggle is turned on, and a denial leaves the toggle on without posting. The tab lays out without its own scroll view inside the host's `ScrollView` and keeps outside-click dismissal. Schedules are local-only: OnlyRemote, widgets and the remote protocol are unchanged.

## Shortcuts settings

Settings → Shortcuts (`AppFeature/Features/Settings/Shortcuts`) mirrors the Evolution layout: a segmented "My Shortcuts" / "Gallery" header, an installed list (menu visibility, a `KeyboardShortcuts.Name(<shortcut name>)` recorder, Open in Shortcuts) and a gallery of `evolutionCard()` cards. `ShortcutsSettingsReducer` (store retained by `SettingsVM.shared.shortcutsStore`) owns the list, the 10-item menu limit and the gallery; every effect goes through the injected `ShortcutsSettingsClient` (the `shortcuts` CLI, `Preferences.shortcutsDic`, `.changeSettings`, `ShortcutAppearanceLoader`, the GitHub gallery with the bundled `ShortcutsMarket.json` fallback, and URL opening). Gallery links are opened only when they are `https`. The installed list reloads when the app becomes active, so Shortcuts added from the gallery show up on return. Row and installed-gallery icons come first from `ShortcutAppearanceCache` (the same cache the menu reads, holding only shown Shortcuts), then from `ShortcutAppearanceLoader.icons(for:)`, one Apple Event per Shortcut, read only while the Shortcuts app is already running; each name is looked up once per session (Refresh re-reads all), and once icons were read the reducer rewrites the shared cache for the shown Shortcuts without further Apple Events. `ShortcutsSettingVM.shared` remains for launch-time hotkey registration and OnlyRemote; both keep the same `shortcutsDic` keys.

## Evolution settings

Settings → Evolution (`AppFeature/Features/Settings/Evolution`) has two tabs: "My Evolutions", a sidebar of saved Evolutions beside an inline editor, and "Gallery". `EvolutionReducer` owns the list, selection, a blank editor for a new item, deletion (always confirmed) and the discard-unsaved-changes prompt; a refresh never replaces an editor with unsaved edits, an in-flight generation or a new item. `EvolutionRowReducer` toggles menu visibility through `EvolutionListService.setActive`, which keeps the existing `UserDefaults.Key.evolutionIDs` list and its order. `EvolutionEditorReducer` keeps a working copy plus the saved original (`isDirty`, Revert), keeps the other control type's scripts while the type is toggled, and lists `missingRequirements` in the footer. `EvolutionCommandEntity.addItem` still only accepts on/off/button commands that passed a test; the editor treats a command identical to the saved one as verified (`makeItem()` marks it `.success`), so renaming or re-iconing an Evolution doesn't re-run its scripts, while any new, edited or generated script must pass ▶ Test first. The icon is saved with the item, not on selection.

Persistence and execution are unchanged so saved Evolutions keep running: the Core Data model, `EvolutionAdapter`, `EvolutionCommandService.executeCommand` (shell commands are still sent as an unescaped `do shell script "<command>"`, prefixed by the `pre-execution` app-storage value), and `KeyboardShortcuts.Name(id.uuidString)`. Because of that unescaped embedding, a stored shell command is the contents of an AppleScript string literal; the editor says so, and generated shell code is converted with `EvolutionShellQuoting.storedForm(ofShell:)`. The editor never rewrites a command the user didn't edit.

Scripts are edited with `ScriptCodeEditor` from the dependency-free `Modules/Sources/ScriptEditor` target: an `NSTextView` with a pure, tested `ScriptTokenizer` (shell and AppleScript keywords, strings, comments, numbers, shell variables; UTF-16 ranges; unterminated constructs run to the end) and dynamic system colours, with smart quotes, dashes, text replacement and spelling correction turned off. On macOS 26 the editor offers "Write scripts with AI": `EvolutionScriptGenerationClient` in `OnlyAgent/EvolutionGeneration` reads `SharedKey.currentAIModel` (never writes it), sends `EvolutionScriptPromptBuilder` instructions with an `AgentSystemInfo` snapshot through `instructedChatStream` (`.agent` purpose), and `EvolutionScriptReplyParser` tolerantly decodes a switch (`turn_on`, `turn_off`, `status`, `status_on_output`) or button reply. Generated scripts only fill the editor (after confirmation when scripts already exist), are marked untested and are never run automatically; only error categories are logged, never the request or reply.

## OnlyRemote tabs

OnlyRemote's Settings → Tabs page is its only tab-visibility control. `RemoteTabConfiguration` keeps Controls locked on; Sound Mixer, Brightness, Screenshots and Aphrodite are hideable alongside the existing optional tabs, persisted by `RemoteTabPreferencesClient` under `tabs.showsSoundMixer`, `tabs.showsBrightness`, `tabs.showsScreenshots` and `tabs.showsAphrodite` (missing means visible). Sound Mixer, Brightness, Screenshots and Aphrodite require OnlyRemote Plus: each renders `RemotePlusGateView` from the shared `RemotePlusAccessFeature` until the entitlement is active, and gating is client-side only. The Dashboard's former bottom Sound Mixer surface was removed; the Sound Mixer tab replaces it.

Protocol 1.8 (`supportsSoundMixerTabRemote`, `supportsBrightnessRemote`) adds `soundMixerSubscriptionUpdate` and `brightnessSubscriptionUpdate` plus `brightnessSnapshot`/`brightnessCommand`, and extends the Sound Mixer contract with per-app equalizer and multi-output routing. `RemoteSoundMixerFeature` and `RemoteBrightnessFeature` follow the System Monitor subscription pattern: they subscribe only while their tab is visible, the app is foregrounded, the selected Mac is authenticated and the user is entitled, so non-members never trigger audio-process enumeration or display scans on the Mac. Neither side persists the streamed state on iOS. A Mac negotiating below 1.8 yields an in-tab upgrade message; older 1.3–1.7 peers keep the legacy `soundMixerSnapshotRequest`/`soundMixerCommand` messages, and new Codable fields decode with defaults.

On the Mac, `RemotePeerSession` version-gates every 1.8 message and owns one cancellable stream task per subscription, stopped on unsubscribe and session end. `RemoteHost` injects `@Sendable` closures that bridge to `SoundMixerVM.remoteSnapshots`/`performRemoteCommand` (mapped by the pure `SoundMixerRemoteBridge`, which exposes bundle-style row IDs and output UIDs but never PIDs, Core Audio object IDs or tap handles) and to the main-actor `RemoteBrightnessProvider`, which counts a subscribed peer as a host of `SettingsVM.shared.brightnessStore`. Snapshots are polled (2 s mixer, 0.4 s brightness) and deduplicated. Commands are clamped and validated against a fresh Mac snapshot; a command that fails because an app, device or display disappeared is dropped without a reply rather than closing the session, and the active stream re-syncs the peer.

Protocol 1.9 (`supportsScreenshotsRemote`) adds the Screenshots tab: `screenshotsSubscriptionUpdate` starts a library stream (`screenshotsLibrary`, polled every 1 s and deduplicated), plus batched `screenshotThumbnailsRequest`/`Result`, `screenshotImageRequest` answered by a manifest and in-order chunks verified with SHA-256, `screenshotDeleteRequest`/`Result`, and `screenshotRequestFailed`. Items are addressed only by `ScreenshotItem.id` plus `revision`; paths never cross the wire and file names are sanitized display names. `RemoteCore` enforces the limits on both sides: ≤ 500 library items, ≤ 12 ids per thumbnail request, thumbnails ≤ 64 KiB JPEG and ≤ 480 px, originals ≤ 48 MiB in chunks ≤ 256 KiB, ≤ 100 ids per delete. On the Mac, `RemoteHost` injects a `RemoteScreenshotsService` (`.unavailable` in tests) built by the main-actor `RemoteScreenshotsProvider` over `SettingsVM.shared.screenshotsStore` and `ScreenshotsClient`; `RemotePeerSession` version-gates every 1.9 message, refuses thumbnail, image and delete requests from a session that has not subscribed, serializes thumbnail work, lets a newer image request cancel the previous transfer, and cancels all screenshot work on unsubscribe or session end. Failed requests reply with `screenshotRequestFailed` and never close the session. Delete goes through `ScreenshotsClient.trash` (pinned items included, matching the Mac's per-item delete); iOS never edits images and has no delete-all.

`RemoteScreenshotsFeature` follows the Brightness subscription pattern and is gated client-side like the other Plus tabs. The root feature syncs the selected Mac and connection state into it through `.contextChanged` rather than mutating child state directly. `RemoteScreenshotCacheClient` persists the library index, thumbnails and downloaded originals per Mac under `Caches/OnlyRemote/Screenshots/<macID>/` (never backed up, excluded from persistence migration); each received library prunes entries whose id and revision are no longer listed, and forgetting a Mac deletes its directory. Offline, the tab shows the cached library with a banner, copy and drag work only for cached originals, and delete is disabled. `RemoteScreenshotImageClient` loads originals cache-first through a single-flight loader keyed by Mac, item and revision, so copy, drag and the detail viewer share one download; `RemoteScreenshotResponses` correlates replies per session and verifies reassembled originals; a newer image request supersedes the in-flight one, so each Mac carries at most one original transfer at a time. Dragging a cell or the viewer's image sends `.dragStarted`, so the reducer starts an uncached original downloading at drag start (a prefetch that neither copies nor opens anything) and the drag provider's own lazy load joins that flight. That matters on iPhone, where a cross-app drag backgrounds OnlyRemote before the drop target asks for the file; on iPad Split View the source stays foreground. Hidden with originals still downloading, the tab keeps its subscription for them only (thumbnails and deletes stop as before) and unsubscribes once they finish or fail, or after `backgroundTransferGracePeriod` (30 s). Every original download runs inside `RemoteConnectionClient.withBackgroundTransferHold`, which spans the fetch and the cache write: while any is in flight, `setForegrounded(false)` stops discovery and reconnects but defers closing the session, holding background time from the injected `RemoteBackgroundTaskClient` (the only `beginBackgroundTask`/`endBackgroundTask` caller), and closes it as usual when the last transfer ends, the 30 s grace period ends, or iOS expires the task. Foregrounding during the hold cancels it and keeps the held session, so nothing resubscribes or reconnects; forgetting, revoking or losing the Mac ends the transfer and with it the hold. The pairing-finalization branch never holds. Copy uses `RemoteScreenshotPasteboardClient` with the original bytes and type. Review demo mode serves a sample library from a temporary-directory cache and never touches a Mac. A Mac below 1.9 yields an in-tab upgrade message.

Protocol 1.10 (`supportsScreenRecordingsRemote`) adds screen recordings to the same messages. `RemoteScreenshotItem` gains an optional `durationSeconds` (decoded if present; negative or non-finite values are dropped) and derives `isRecording` from `contentType` conforming to `.movie`. Originals are limited by type through `RemoteScreenshotLimits.maximumTransferBytes(contentType:)`: images stay at 48 MiB, recordings may be up to 512 MiB (`maximumRecordingBytes`), and chunks stay at 256 KiB. The Mac gates on the negotiated version: `RemotePeerSession` passes `includesRecordings` to `RemoteScreenshotsService.libraries` and `image`, so a peer below 1.10 never sees a recording item or original, and the provider memoizes durations per id and revision across library polls, loading new ones eight at a time and dropping those of items that left. Thumbnails of recordings are poster-frame JPEGs. The provider maps originals with `.alwaysMapped`, and the session sends the manifest and then encodes one chunk at a time (`RemoteScreenshotImageEncoder.manifest`/`chunk`), so a large recording is never copied whole. On iOS, `RemoteScreenshotResponses` writes every original, image or recording, through a `RemoteScreenshotFileAssembler` (a single-owner class) into `tmp/OnlyRemoteTransfers`, hashing incrementally; any failure, timeout, cancellation or `finishAll()` discards the partial file, a delivered file is removed if its receiver has gone, and the live connection client deletes it if the selected Mac or session changed while it was in flight. `RemoteScreenshotImagePayload` carries that verified file, and `RemoteScreenshotCacheClient.saveImage` moves it into the per-Mac cache, replacing any older copy; the image client deletes it if saving fails. The 20 s inactivity timeout applies between chunks, not to the whole transfer. In the tab, recording cells show a video badge with the duration, tapping downloads the original and the viewer plays it with AVKit (the poster frame shows meanwhile), and Copy is hidden in the cell, the viewer and accessibility actions while the reducer ignores `copyTapped` for recordings. The drag provider registers the item's own movie type, and recordings over the limit or changed on the Mac report "too large to transfer". Downloaded recordings stay in the per-Mac cache until they leave the library, with no separate size budget.

## Xcode Cleaner

`Modules/Sources/XcodeCleaner` owns the macOS Settings cleaner, its TCA state and views, and an injected `XcodeCleanerClient`. SettingsVM retains the store for the app session. No cleanup API is exposed to widgets, OnlyRemote, or deeplinks. Inventory and cleanup authorization remain in memory.

Filesystem inventory is restricted to the current user's standard DerivedData, Xcode cache, SwiftPM cache/download, CoreSimulator cache/log, and Xcode DeviceSupport directories. DerivedData includes its nested Build, Index, ModuleCache, and SourcePackages artifacts exactly once. Archives, source repositories, Xcode.app, SDKs, credentials, and custom project build directories are excluded. Cleanup preserves category roots, rejects symbolic-link ancestors and changed root identities, and reports individual failures. There is no privilege escalation. Sizes use allocated file bytes and represent unknown or partial inventories explicitly.

Simulator devices and runtime images are inventoried through an injected argument-array `simctl` command boundary. Device/runtime and DeviceSupport deletion require item-specific confirmation. Device deletion requires a fresh shutdown inventory; runtime deletion requires the runtime-image UUID, removable metadata, and no booted device using it. Raw simulator/runtime directory deletion is forbidden. The owned command process has bounded captured output, a timeout, and cancellation; scanning and file operations run outside the main actor. Focused temporary-fixture and reducer tests never clean live developer data.

Tab visibility uses the exportable `showXcodeCleanerTabKey`, defaulting to true, edited on the Settings → Tabs page. The former built-in switch is deprecated (see Tab visibility). The cleaner is local-only: widget entity discovery, remote catalogs/status and forged remote action routing exclude it. The previous Xcode DerivedData cleanup action keeps its existing identity and behavior.

Settings, OnlySwitch's menu-bar list, and OnlyControl share `SettingsVM.shared.xcodeCleanerStore` and its current snapshot authorization. Panel hosts own scrolling and request a compact presentation where appropriate. The cleaner supports session-only multi-selection and freezes each confirmed batch as an ordered item list with its original snapshot and host-owned confirmation token. Filesystem and simulator adapters retain bounded immutable authorization contexts, independently pinning the displayed context and in-flight cleanup. ## App Uninstaller

`Modules/Sources/AppUninstaller` owns the macOS-only uninstaller domain, TCA feature, native presentation and injected `AppUninstallerClient`. `SettingsVM.shared.appUninstallerStore` retains session state across Settings, the menu-bar list and OnlyControl. The feature accepts one local application bundle through a file drop or native chooser; selection and confirmation remain reducer-owned. Host-specific confirmation tokens freeze the accepted inventory and ordered selection. A disappearing host dismisses its pending confirmation, scanning is cancelled after the last visible host leaves, and an already confirmed removal continues independently of presentation.

Inventory includes the chosen `.app` and only exact bundle-identifier matches in the current user's `Library/Preferences/<identifier>.plist`, `Library/Caches/<identifier>`, `Library/Application Support/<identifier>`, `Library/Saved Application State/<identifier>.savedState`, `Library/Logs/<identifier>` and `Library/Containers/<identifier>`. ByHost preferences additionally require the exact `<identifier>.<UUID>.plist` filename structure. The feature does not guess by app name, enumerate arbitrary home locations, remove shared group containers, or manage keychains, launch agents, receipts or system Library files. Full Disk Access can expose additional matches within this allowlist; it does not expand the discovery policy. Inaccessible files and unknown sizes are explicit, so an accepted inventory is not a claim that all related app data has been discovered.

The filesystem actor keeps bounded immutable scan authorizations in memory and pins the displayed context. Removal accepts snapshot and item identifiers, never arbitrary caller-provided paths. Before each item it rechecks app metadata, running-app state, file and ancestor identities, and the protected-location/self-app policy. User-controlled symbolic links and symbolic-link ancestors are rejected; only the known root-owned macOS `/var`, `/tmp` and `/etc` aliases are permitted and identity-pinned. System/Apple apps, apps nested inside another app, OnlySwitch itself, running apps and bundles on excluded system/network/volume paths are not eligible. Associated files are processed before the application bundle, and successful item authorizations are consumed to prevent replay. A single removal batch is admitted at a time, with individual outcomes retained for failed items. If a selected associated file fails, other selected data files continue but the application bundle remains available for a safe retry.

Every removal requires an explicit review and confirmation of selected files, and uses `FileManager.trashItem` through an injected effect. When that move fails with a permission error (for example a root-owned app in `/Applications`) and the item has already passed revalidation, the injected `privilegedTrash` effect (`AdministratorTrash`) asks macOS for an administrator password and moves that one item into the user's `~/.Trash` with `/bin/mv -n` via AppleScript `with administrator privileges`; paths reach the shell only through `quoted form of`. Cancelling the password prompt is reported as `App Uninstaller Authorization Cancelled` and keeps the item; other errors never prompt. There is no permanent deletion, automatic app termination or restart. Filesystem work runs outside the main actor; the chooser, running-app lookup and privacy-settings navigation use explicit main-actor boundaries. Identity revalidation reduces accidental or stale-path removal, but path-based Trash operations cannot provide an atomic guarantee against a hostile same-user process substituting a path between the final check and the move.

Tab visibility uses the exportable `showAppUninstallerTabKey` preference, defaulting to true, edited on the Settings → Tabs page. The former built-in switch is deprecated (see Tab visibility). Hiding the selected list/OnlyControl tab returns to controls; Settings remains an entry point. The uninstaller is local-only: widget discovery, remote catalogs/status and forged remote action routing exclude it, and no destructive deeplink is exposed. Focused fixture and reducer tests use temporary app/Library trees and an injected Trash recorder; verification never uninstalls a real user application.

The list and OnlyControl suppress outside-click dismissal while their own App Uninstaller section is selected, allowing Finder selection and dragging; explicit close and status-item toggling remain available.

## Screenshots

`Modules/Sources/Screenshots` owns the macOS-only screenshot and screen-recording library (shown as the "Screenshots & Record" tab; persisted identifiers such as `SettingItem.Screenshots`, `showScreenshotsTab`, `openScreenshotsTab`, the folder and the manifest keep their screenshot names), `com.apple.screencapture` takeover, folder watcher, thumbnail loading, annotation renderer, TCA list/editor features, views and injected `ScreenshotsClient`. `SettingsVM.shared.screenshotsStore` retains one session store across Settings, the menu-bar list and OnlyControl. Takeover is opt-in and defaults off: enabling it backs up the user's legacy `location`, macOS 27+ `location-screenshot`, and `show-thumbnail` values once, then uses the location key for the running macOS version to point capture at `~/Pictures/OnlySwitch Screenshots` with the floating thumbnail off. The same toggle also redirects the iOS Simulator's `com.apple.iphonesimulator` `ScreenShotSaveLocation` to that folder via `SimulatorScreenshotPreferences`, with its own one-time backup; if that write fails the system takeover is rolled back, and installs that enabled collection before this existed are migrated once on load. Xcode's Device Hub (`com.apple.dt.Devices`) keeps the same key inside its sandbox container, which other apps cannot write, so while collection is on the feature runs `ScreenshotsClient.collectExternalCaptures`: `DeviceHubScreenshotImporter` watches `~/Desktop` and moves new images whose `com.apple.quarantine` agent is `DeviceHub` into the library folder (never replacing a file), where the library watcher records them; files already on the Desktop and files from other apps are untouched, and the effect is cancelled when collection turns off. Disabling restores the backed-up values exactly, but never overwrites a value changed elsewhere after enabling, which the feature reports as `changedElsewhere` with a Reapply action. Failed writes are reverted and reported. A JSON manifest in Application Support records items by UUID; every pin, trash, edit and file-URL lookup resolves through that record, never a caller-supplied path, and symbolic links, nested paths and duplicate names are rejected; plain image files found directly in the folder are adopted into the manifest on load. Deletion only uses `FileManager.trashItem`; delete-all asks for confirmation and keeps pinned items. The editor keeps undo/redo in its session and overwrites the original file in its original format only on Save. Its preview and export share a strong Gaussian blur routine; the editor caches the blurred source once and clips it to draft/committed regions before drawing vector annotations, so dragging does not rerun the filter. Image preparation and save rendering run outside the main actor. A new capture is revealed and flown into the list through the injected `ScreenshotPresentationClient` (Reduce Motion fades instead; a hidden tab collects without revealing). App-side `ScreenshotSectionRevealFeature` retains the target host’s pending selection before the reveal notification opens its window; the matching popover or OnlyControl host selects Screenshots and acknowledges the request when mounted, so cold startup cannot lose navigation and normal reopening does not replay it. The Screenshots settings page exposes a `KeyboardShortcuts` binding (`openScreenshotsTab`) with no assigned default. Its controller checks the active host’s visibility and exact section before routing: it closes an already visible Screenshots tab, otherwise selects and reveals Screenshots even with collection off. Hidden tabs reject the action while retaining the binding. Automatic captures continue to reveal without toggling the host closed. Like the App Uninstaller, the list and OnlyControl retain outside clicks while `.screenshots` is selected. There is no built-in switch, widget, deeplink or OpenClaw exposure. OnlyRemote Plus can view, copy, drag and trash library items through `RemoteScreenshotsService`/`RemoteScreenshotsProvider` (see OnlyRemote tabs); remote delete moves files to the Trash and remote clients never edit them. Known limitations: clipboard-only captures (⌃⇧⌘3/4) are not collected.

Screen recordings share the folder, manifest and item record with screenshots. `ScreenshotMediaType` is derived from the file extension (`UTType` conforming to `.image` or `.movie`, hidden names excluded), so the manifest format is unchanged and `ScreenshotLibrary.isMediaName` adopts and adds both kinds. The folder watcher's `ScreenshotFileCompleteness` records an image once it decodes completely and a movie once its size has settled and its top-level ISO-BMFF/QuickTime boxes contain a complete `moov` box, which the recorder writes when it finalises the file. A settled image that never decodes is abandoned after 40 checks; a movie keeps being checked for about 10 minutes, because a recorder writing to its final name can pause before finalising. `ScreenshotMediaInspector` reads a poster frame (preferred track transform applied) and the duration with AVFoundation; the thumbnail cache, the fly-in and the client's `duration` effect use it, and the cell shows a video badge with the duration. On macOS 14–26 the `location` key already covers ⇧⌘5 recordings. On macOS 27+ `screencaptureui` reads `location-screenrecording` separately, so `ScreenCapturePreferences` backs it up once (`screenRecordingLocationBackedUp`), points it at the folder, includes it in `changedElsewhere` detection, and restores it on disable only while it still points at the folder. Installs that enabled collection before this was taken over are migrated once on load (`needsRecordingMigration`, `migrateRecordingLocation()`): only the recording location and its backup are written, and only while a valid backup exists and the screenshot location is still ours; if the user changed it elsewhere the migration is skipped and Reapply is left to them. The legacy Simulator saves recordings to the already-redirected `ScreenShotSaveLocation`, and `DeviceHubScreenshotImporter` moves Device Hub recordings from the Desktop like its screenshots. Recordings are never editable: the cell has no edit button or accessibility action and `ScreenshotsFeature` ignores `editTapped` for them. Copy writes only the file URL for a recording, and open, pin and delete use neutral item names in accessibility. Recordings written by `xcrun simctl io … recordVideo` go wherever the caller writes them and are not collected.

## Sound Mixer EQ

`Modules/Sources/SoundMixerEQ` owns validated ten-band settings, per-source TCA disclosure/edit state, injected persistence/audio effects and the compact editor. `SoundMixerVM.shared` retains the store across menu-bar and OnlyControl presentations and resolves row IDs to current Core Audio handles. Bundle identifiers persist requested settings; PID-only sources remain session-only. EQ does not alter widget contracts; OnlyRemote reaches it only through the protocol 1.8 Sound Mixer bridge (see OnlyRemote tabs). Native Music/Spotify volume still uses the existing scripting path; its separate EQ tap applies unity gain.

`CSoundMixerEQ` owns fixed-capacity stereo biquad histories and a lock-free C11 coefficient mailbox. Coefficients are computed on the control side, published as atomic slots under a revision, and consumed once per callback without retrying or waiting. Two preallocated filter banks crossfade revisions; each channel has independent history. The realtime IOProc calls only C processing with no allocation, blocking, Swift ARC, or actor access. Atomic gain, retirement and audio-received flags replace shared mutable Swift callback state. Retired callback allocations retain the existing process-lifetime policy to protect late callbacks after Core Audio teardown.

EQ requires macOS 14.4 process taps; macOS 14.0–14.3 keeps native scripting volume and presents an availability message. A chain exists only for reduced volume or nonflat EQ, and reconciles process membership and output device/rate before reuse. A default-output listener rebuilds active chains even while the panel is closed. Unsupported tap/output formats and partial setup failures tear down the chain so original audio resumes. The feature distinguishes requested settings from confirmed audio reception, retaining pending settings for idle sources and showing permission/setup feedback without claiming playback success. Disabling the mixer cancels feature effects and releases taps; refresh generations prevent suspended reads from restoring disabled rows.

Aggregate input must be an unambiguous stereo Float32 stream. Devices that add physical microphone inputs to the aggregate are rejected before starting IO, preserving original audio rather than treating microphone samples as the tapped app. Supporting those layouts requires explicit tap-stream identification.

OnlySwitch's radio and background-noise source uses the stable `onlyswitch.own-playback` row identifier for EQ and output preferences. Its native player retains volume control upstream, while EQ and routing use unity gain. Playback runs in an owned child process of the app executable, dispatched before SwiftUI application initialization. Bounded local pipe messages carry playback intent, metadata and spectrum data; the child stops when its parent closes the pipe. The main process captures only that child's exact audio process IDs, authorizing the retained process's PID and per-launch generation before tap reuse and reconstruction. It never captures the host process, whose output includes other apps' processed audio. Stopping playback or disabling Mixer releases the child's tap; flat EQ and system-following output preserve native playback. OnlyRemote uses the same registered source and existing EQ/routing commands without a protocol change.


### Per-App Output Routing

`SoundMixerEQ.OutputRoutingFeature` retains each App's independent output selection and requested/applied status through an injected `OutputRoutingClient`. Empty selection follows the system output without changing it; nonempty selections persist stable output UIDs per bundle identifier, bounded to sixteen devices. PID-only sources are session-only. Missing UIDs remain selected: a connected subset receives audio, while an entirely disconnected selection releases its chain and explicitly waits for reconnection. Offline device names are session metadata, not persisted identifiers. The existing bottom System Output row remains a read-only default-device summary. Each App expands its own inline output checkbox list, independently of EQ disclosure; selections keep the list open in the host window and use the host’s existing scrolling, avoiding child-window outside-click dismissal.

`SoundMixerService` inventories alive output endpoints and their format/layout fingerprints, excluding OnlySwitch's own private aggregate devices. `SystemAudioMixer` resolves current endpoints together with the App's gain and EQ, then creates one private, nonstacked aggregate per App. Active-subdevice IDs/UIDs establish actual device ordering; aggregate buffer layouts and every output stream's Float32 sample format/rate must confirm the complete channel map before IO starts. The main clock is deterministic, other subdevices and the process tap use drift compensation, and the existing stereo-only input guard rejects ambiguous hardware microphone inputs. Explicit routes retain a tap even for unity gain and flat EQ.

`CSoundMixerEQ.OSEQCreateRouted` validates and copies immutable, nonoverlapping endpoint ranges (sixteen outputs, up to sixty-four channels each, total at most 1024). Rendering advances the stereo EQ/gain once per source frame, then fans the result to every selected range. Mono destinations receive the stereo average, wider destinations receive L/R on their first two channels, and unused channels/trailing data are zeroed. The callback performs no allocation or device queries.

Device-list/default-device and physical format/rate/alive listeners continue while panels are closed. Snapshots include actual output stream formats and buffer channel layouts; identical HAL notifications, including private aggregate creation/removal, do not trigger reconstruction or retry loops. Configurations reconcile only against live endpoints, and source ownership is revalidated before reconnecting stale process handles. Source exit and Mixer disable release chains; persisted routing intent is restored by the feature when a source/device returns. Core Audio clock synchronization, transport latency, and perceived alignment across physical devices require live hardware verification beyond deterministic renderer tests.

## Display Volume over DDC

The Sound Mixer's system slider uses macOS volume when the default output exposes a settable virtual main volume. DisplayPort/HDMI display audio usually does not, so `SoundMixerService` then targets the display over DDC/CI (VCP `0x62`), and greys out the slider when neither path works. `Modules/Sources/DisplayDDC` owns pure, tested DDC packet framing, reply validation and display matching, plus `DDCDisplayController`, which resolves Apple Silicon's private `IOAVService` I2C symbols at runtime (as MonitorControl does) and serializes blocking I2C on its own queue. An audio device is matched to an external display by EDID product name; a single external display is used even when names differ, and several candidates are never guessed. Intel Macs and displays that do not answer DDC report the control as unavailable.

While the Sound Mixer is enabled and the output is reached over DDC, `SoundMixerVM` opens the gate of `DisplayVolumeKeyTap`, a session-level `CGEvent` tap on its own thread that consumes volume up/down/mute media keys (decoded by `DisplayDDC.VolumeKeyEvent`) and forwards key-downs to the main actor. Steps follow macOS (1/16, Shift+Option 1/64, `DisplayVolumeLevel`) and reuse the slider's rate-limited write path. For any other output the tap is stopped and macOS handles the keys. Consuming keys requires Accessibility: the user is prompted once per launch, the panel shows a hint with a System Settings link, and the `com.apple.accessibility.api` distributed notification restarts the tap once access is granted. Feedback is OnlySwitch's own `DisplayVolumeHUD` (Liquid Glass on macOS 26+, material before), because the private `OSDUIHelper` HUD draws nothing on macOS 26+. Another app that also intercepts volume keys (e.g. MonitorControl's keyboard control) must be disabled to avoid double handling.


## Display brightness

`Modules/Sources/DisplayBrightness` owns the brightness domain, mapping policy, cancellable coordinator and TCA presentation. `SettingsVM.shared.brightnessStore` serves the menu-bar list, OnlyControl and Settings → Display. `DisplayBrightnessClient` injects discovery, writes, observation, persistence and software-dimming reset; views only render state and send intent. The optional Brightness tab uses the exportable `showBrightnessTabKey`, managed in Settings → Tabs.

The app's main-actor `DisplayBrightnessService` adapts DisplayServices for readable native displays and click-through AppKit shade panels for software dimming. External hardware brightness uses `DisplayDDC.DDCDisplayController`, sharing its serial I2C queue with Sound Mixer's display volume. A valid, unique vendor/product/serial association is required to target a screen through DDC. On Apple Silicon sibling-framebuffer layouts, discovery additionally matches the exact endpoint connector and shared provider-family identity; ambiguous or unsupported hardware uses explicitly labeled software dimming. No display-name or enumeration-order guess may select a hardware target. DDC writes report transport submission, not a hardware acknowledgment.

Smooth changes retain only the latest per-screen intent, revalidate inventory generations after suspensions and bound DDC write frequency. A lock-protected transport gate rejects cancelled or superseded queued luminance writes before I2C; `BrightnessOutputWriter` revalidates topology, recovery policy and per-screen intent after asynchronous hardware work before applying any software shade. Combined dimming maps the bottom 20% to software dimming at the display's hardware minimum. Software transmission is clamped to at least 10% by default; full black requires the explicit zero-brightness setting. Reset clears shades, and sleep/topology changes invalidate transitions and discard shades so a reconnect or wake cannot restore a stale black image. Panels remain click-through, leave menu/status recovery UI accessible, and disappear on process exit. The feature never modifies gamma tables or powers monitors off to implement minimum brightness.

The existing `syncExternalBrightnessKey` remains the synchronization preference. The legacy sync entry point delegates to the new service instead of maintaining a second DDC writer. Enabling sync or discovering a new topology aligns external displays to the current readable native source, preferring the built-in display. Thereafter, changes from any native display can drive sync; if multiple readings change in one poll, built-in displays take priority, followed by display ID. Sync targets other controllable external displays, including native ones, and suppresses feedback from mirrored writes and Dim Screen. Startup reads current hardware rather than restoring saved brightness. Live per-screen levels and connection identifiers are not exported or persisted. Manual native-slider changes end an active Dim Screen session without restoring its captured brightness over the newer user intent.

No widget capability or deeplink is exposed; the only remote path is the protocol 1.8 Brightness bridge (see OnlyRemote tabs), and sliders do not require Accessibility permission. Actual DDC compatibility, HDR/software-shade coverage, fullscreen/Spaces behavior and optical transition quality require hardware verification in addition to deterministic tests.


### Keyboard brightness controls

`DisplayBrightnessKeyboardController` owns a separate `DisplayBrightnessKeyTap`; Sound Mixer's volume tap is unchanged. The tap recognizes only system-defined brightness media keys (codes 2/3, auxiliary subtype 8), consumes matched down/repeat/up gestures for the external screen under the live Quartz pointer, and leaves built-in-screen, volume, keyboard-illumination and ordinary function-key events with macOS. Immutable screen bounds and topology identifiers cross the callback boundary under a lock; hardware work never runs on the event-tap thread. A captured gesture freezes its target. A topology-only change suppresses the rest of that already captured gesture without writing until release, so a refresh cannot redirect held repeats into built-in brightness.

The exportable `controlWithBrightnessKeysKey` preference defaults to true and appears in Settings → Display. Keyboard interception needs Accessibility; sliders do not. No permission prompt is issued at launch or during discovery. The explicit System Settings action invokes the injected permission effect, and the panel/settings show denied or unavailable status. Permission changes are rechecked while eligible; denial, revocation, sleep and explicit disable stop capture and preserve system handling. Event-tap startup/stop are asynchronous and session-gated to prevent stale callbacks from a previous thread.

Keys use 1/16 steps, or 1/64 with Shift+Option. `BrightnessKeyAccumulator` records pending desired levels synchronously so queued repeats accumulate before asynchronous hardware writes start. The service cancels obsolete per-screen keyboard tasks and sends accepted targets through the same coordinator, policy and DDC queue as sliders. Internal intents expose the UI revision they supersede; the TCA reducer cancels only that older pending slider effect and ignores its delayed completion/failure while preserving any newer slider intent. No global keyboard event or display identity is persisted. Live media-key delivery/Accessibility behavior requires manual verification; focused tests do not synthesize keyboard events or change real display brightness.
